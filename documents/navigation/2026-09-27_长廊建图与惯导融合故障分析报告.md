# 长廊建图与惯导融合故障分析报告

**分析日期：** 2026-09-27  
**对象：** M10P 二维激光、C 板 IMU、RF2O、`robot_localization` EKF、估计保护器与 SLAM Toolbox 组成的履带机器人建图链路  
**用途：** 故障复盘、方案评审与下一轮受控实验的依据

## 一、汇报摘要

当前问题不是“IMU 接入后算法必然变差”，也不能归结为某一个回环参数。已有证据显示，系统同时存在四类问题：

1. **目标场景的观测缺口没有补上。** 长直、近似平行的走廊墙面主要约束横向位置和航向，沿走廊方向的位移约束弱。现有链路缺少可信的独立实测行驶距离；稳定的陀螺角速度不能代替纵向速度。将 EKF 换成 ESKF 或只调整回环阈值，不会凭空增加该方向的信息。
2. **新接入的数据和保护链路引入了失效通道。** 现场惯性里程计多次因加速度越限或数据间断失效；激光质量标志、速度上限、EKF 候选位姿跳变又触发保护器暂停和重置。局部测量故障在某些状态下被放大成公共里程计/TF 中断，继而影响建图。
3. **扫描时间链路只完成了部分修复。** 后一次运行的 TF 丢扫描日志明显下降，但 `LaserScan` 逐束时间仍为零。整圈约 83 ms，快速转向时不能据此认定已经消除扫描运动畸变。
4. **评估方法不足以证明哪次改动改善或损害了精度。** 三次录包的轨迹、速度和时长不同；没有独立位置真值、可信实车速度或回环修正前后配对数据。地图截图可证明存在视觉异常，不能单独证明其成因。

**工程判断：** 先恢复可复现的纯激光基线，完成时间/TF/串口数据质量核验，再做“纯激光 → 激光＋陀螺 → 加入加速度”的同包回放对照。若长廊纵向误差仍达不到要求，优先增加带打滑检测的实测履带/轮位移，或布设可重复识别的纵向地标；其后再决定是否值得开发二维激光与 IMU 的紧耦合前端。

| 判断 | 证据等级 | 汇报时的准确说法 |
| --- | --- | --- |
| 惯性里程计多次因加速度门槛失效，保护器多次暂停 | 录包直接观测 | 可以作为已确认的可用性问题。 |
| 长廊纵向几何约束弱，现有链路缺少可信独立位移 | 几何机制与现场配置共同支持 | 可以作为主要设计缺口；具体纵向误差仍需外部真值测量。 |
| 当前时间修复尚未证明逐束采样时间正确 | 消息契约与运行参数支持 | 可以列为待闭环的高优先级风险，不能宣布它已造成全部地图畸变。 |
| C 板硬件损坏、某次参数修改导致精度下降、回环造成图像飘移 | 现有证据不足 | 应列为待验证假设，不应写成事故结论。 |

## 二、系统实际在融合什么

11:26 故障包保存的运行参数显示，EKF 以 30 Hz 工作：`odom0=/chassis/odom/laser` 提供 `x/y/yaw`，`imu0=/chassis/imu/gyro` 提供 `wz`，`imu1=/chassis/imu/acceleration` 提供 `ax/ay`。静止零速度和退化时的部分速度也是输入，但它们仍由同一套扫描/状态判断导出。独立惯性里程计以激光里程计作锚点。因此“激光、INS、EKF 三条曲线”并不是三个相互独立的绝对位置传感器；它们一致只能说明链路内部一致，不能证明对真实位置准确。[现场 EKF 参数](/home/hi/incident_20260927_112652_702592/incident_20260927_112652_702592/snapshots/live/0001_20260927_112713/params__ekf_filter_node.yaml)、[惯性里程计参数](/home/hi/incident_20260927_112652_702592/incident_20260927_112652_702592/snapshots/live/0001_20260927_112713/params__tracked_inertial_odometry.yaml)。`robot_localization` 官方配置指南也要求注意同一来源的重复信息不能当作独立测量：[配置指南](https://github.com/cra-ros-pkg/robot_localization/blob/rolling-devel/doc/configuring_robot_localization.rst)。

```text
M10P /scan ──> RF2O ──> 激光里程计 ───────┐
                │                       ├──> EKF 候选位姿 ──> 估计保护器 ──> 公开 odom/TF
                └──> 质量/静止/部分速度 ────┤                         │
C 板 IMU ──> 陀螺/加速度预处理 ───────────┘                         └──> 扫描建图门控
                 └──> 激光锚定惯性里程计 ─────────────────────────────┘
                                              /scan_slam + odom/TF ──> SLAM Toolbox ──> map→odom
```

这属于**已完成里程计结果的松耦合滤波，加上输出保护和状态切换**，不是把激光原始几何残差与 IMU 预积分放进同一个优化问题。FAST-LIO2 的官方实现使用激光点与 IMU 的紧耦合前端，并强调逐点时间对运动去畸变的重要性；当前二维 `/scan` 链路不能直接替换成该实现：[FAST-LIO 官方仓库](https://github.com/hku-mars/FAST_LIO)。

## 四、根因分解

### 4.1 长廊的纵向位移弱可观测：需求与传感器能力不匹配

以走廊方向为 x、横向为 y。两侧近似平行的长墙即使扫描非常清晰，也主要告诉匹配器机器人离墙有多远、朝向是否偏斜；只沿 x 平移一小段时，墙的局部形状几乎不变。如果看不到走廊端点、门框、柱子或有区分度的侧向结构，连续匹配的纵向误差会积累。二维激光室内几何重复场景的退化及轮速参与融合，已有直接研究：[2DLIW-SLAM 原论文](https://arxiv.org/abs/2404.07644)。

陀螺仪改善的是短时转角传播，不测量走过的距离；在匀速阶段，理想加速度接近零。加速度偏置积分一次成为速度误差，再积分成为位置误差；对一个不稳定且偶有断流的 IMU，平滑可削减高频噪声，但不能消除未知偏置、错误标定或缺失的纵向外部约束。ESKF、IMU 预积分和更复杂的噪声模型可以改进估计器实现，却不能解决“没有新增有效纵向观测”的问题。

### 4.2 惯导可用性与质量门槛不匹配

现场 IMU 处理已包含固定安装旋转、静止加速度基线、0.04 s 平滑、0.8 m/s² 尖峰判别和可疑样本方差放大；但惯性里程计仍以 1.5 m/s² 为平面加速度上限。[预处理参数](/home/hi/incident_20260927_112652_702592/incident_20260927_112652_702592/snapshots/live/0001_20260927_112713/params__tracked_imu_acceleration.yaml)。11:26 包的 p95 远高于该上限，现场也直接记录到多次惯导失效；这证明门槛与当次部分测量不相容，**不证明所有运动阶段都不可用**。09:05 包还录到原始 IMU 及预处理数据间断。串口连接问题是待检查的合理假设，但录包本身不能区分 USB/串口、电源、固件丢帧、机械振动和标定误差。

EKF 现场参数中的测量拒收阈值约为 `1.8e308`，数值上近于关闭该级残差拒收；异常主要依赖前处理和后级保护。后级保护能够拒绝危险输出，却发生在候选位姿形成之后。不能据此断言每一个原始尖峰都已污染 EKF；必须按消息时间关联原始值、预处理值、创新量和保护状态才能证明单次传播路径。[现场 EKF 参数](/home/hi/incident_20260927_112652_702592/incident_20260927_112652_702592/snapshots/live/0001_20260927_112713/params__ekf_filter_node.yaml)。

### 4.3 保护状态机把局部异常放大成输出断续

保护器同时检查候选位姿连续性、与激光的一致性、测量年龄和各后备源的有效期限。保护本身有必要；问题是当激光标志抖动、惯导也因加速度越限不可用时，链路会进入暂停、复位、重新预热及交接循环。10:41 包反复出现输出过期，11:26 包则以激光质量和估计速度门槛为主要首发原因。公开 `odom→base_footprint` 的可查询区间随之缩短，SLAM 对扫描的处理受到影响。SLAM Toolbox 官方接口明确依赖扫描和有效的 `odom→base` 变换：[项目文档](https://github.com/SteveMacenski/slam_toolbox)。

11:26 现场建图门控同时设置 `require_imu_ready=true`、`require_imu_samples=true` 和 `allow_laser_only_state=true`。这表示即使估计状态允许使用激光单源，IMU 完全掉线时建图入口仍可能被 IMU 就绪条件挡住，**“允许激光单源”和“与 IMU 断连解耦”并不等价**。这是配置层面可以直接复核的耦合点；具体一次暂停是否由它造成，仍应查对应时间的门控原因日志。[现场建图门控参数](/home/hi/incident_20260927_112652_702592/incident_20260927_112652_702592/snapshots/live/0001_20260927_112713/params__kiwi_mapping_scan_gate.yaml)。

“不暂停”和“继续正确建图”不是同一目标。现场 11:26 参数允许 `LASER` 单源状态写 `/scan_slam`，该状态约占 22% 的状态心跳。若仅为避免停顿而允许单源或预测位姿继续固化地图，地图可能更连贯地累积误差。事后已将建图门控改为只在 `VALID` 状态写图；这项措施控制了错误固化风险，但可能减少可用于建图的扫描，不能替代位姿精度提升。[现场建图门控参数](/home/hi/incident_20260927_112652_702592/incident_20260927_112652_702592/snapshots/live/0001_20260927_112713/params__kiwi_mapping_scan_gate.yaml)。

### 4.4 扫描时间与运动畸变仍未闭环验证

10:41 包中 `/scan` 的 `scan_time` 为 0，11:26 包约为 0.083 s，接收时间与头时间之差中位数由约 2 ms 变为约 44 ms；SLAM 的 TF 丢扫描日志从 27 条降为 1 条。**这证明 TF 排队症状改善，不证明每束激光使用了正确位姿。** ROS 2 `LaserScan` 消息规范要求头时间表示首束采样时刻，`time_increment` 表示相邻束时间：[消息定义](https://github.com/ros2/common_interfaces/blob/humble/sensor_msgs/msg/LaserScan.msg)。现场按角度排列的束序与真实采集顺序是否一致尚未核实，11:26 包 `time_increment` 仍为 0；将时间参考前移半圈不能直接证明满足首束时间契约。

按 11:26 包陀螺角速度 p95 估算，83 ms 内可能旋转约 3.5°，前包相应估算约 0.8°。这是运动畸变风险的量级估计，受陀螺比例标定和实际转动影响；尚不能断言它造成了截图中的具体射线形状。两包第一张原始地图已出现放射状空闲射线，提示应首先检查原始扫描、无效点/角度、时间、外参和对应位姿，而不能把射线归咎于后期回环。[首图对比](/home/hi/incident_20260927_112652_702592/analysis/initial_map_comparison.png)。

### 4.5 回环问题的证据不足

目前故障包没有一组可验证的“同一次回环修正前位姿/地图”和“修正后位姿/地图”。已有图节点跟踪未观察到已存在节点移动超过 1 cm；两包首图也已存在异常射线。因此**“回环后看起来飘”是现场观察，“回环导致地图变形”尚未证实**。排查回环时，若现场安装版本提供相关接口，应另录 `/slam_toolbox/loop_closure_event`、`/slam_toolbox/new_node_event`、`/slam_toolbox/pose_graph`；否则保存事件日志和序列化图。还应在同一次事件前后保存图和地图，量化回环残差、节点位移及 `map→odom` 校正。不能用不同时间、不同路径的地图快照伪造修正前后对比。SLAM Toolbox 对这些事件和图话题的说明见[官方文档](https://github.com/SteveMacenski/slam_toolbox)。

## 五、为什么纯激光版本在现场看起来更好

纯激光链路在特征较丰富的区域只依赖一套扫描匹配里程计和一条 TF 输出，没有额外的 IMU 加速度失效、激光/INS/EKF 交接及重置循环，**连续性上天然少了若干故障点**。这足以解释“加入惯导后经常更难用”的工程现象，却不能证明纯激光在长廊中的绝对位置精度更高。无外部真值时，RViz 中的地图顺滑、几条同源曲线接近，都不等于纵向误差小。两次后续录包转速和运行时长明显不同，更不能据此得出某一改动使精度单调下降的量化结论。

## 六、解决路径与优先级

| 优先级 | 动作 | 要解决的具体问题 | 必须留下的验收证据 |
| --- | --- | --- | --- |
| P0 | 冻结一次纯激光基线及现场二进制/参数版本；同一条长廊以相近速度采集往返和小闭环，录原始扫描、IMU、串口健康、实际位移参考、TF、EKF 创新和状态机原因。 | 消除“版本不一致”和“不同工况互相比”的解释歧义。 | 包哈希、提交号/工作区差异、完整参数快照、独立量距或可复核的视频地标；明确业务允许的纵向误差。 |
| P0 | 核验 `/scan` 每一束的采样顺序、首束时间、圈周期、角度方向和 TF 时效；验证雷达/IMU 外参及陀螺比例、偏置。对没有逐束时间的扫描，先限制转速做基线。 | 排除时间、外参和整圈运动畸变。 | 原始协议时间到 `/scan` 索引的对应表；回放中扫描时刻 TF 可查询率、丢扫描数、原始扫描与静态墙几何残差。 |
| P1 | 同包离线回放三组：纯激光；激光＋仅 `wz`；激光＋`wz`＋`ax/ay`。每组使用相同扫描、轨迹和 SLAM 参数；不要同时调保护门槛和回环参数。 | 确定 IMU 的哪一部分产生净收益或净损失。 | 长廊纵向/横向误差、航向误差、暂停次数与持续时间、TF 缺口、地图墙线重影、回环前后残差。 |
| P1 | 分离“供导航连续使用的短时预测”和“允许固化地图的高可信状态”；对单源异常采取有界协方差增大、超时和连续交接，不让单个短暂越限造成无条件全链重置。 | 降低反复暂停，同时不把预测误差写进地图。 | 故障注入：单次 IMU 尖峰、0.2–1 s 断流、激光质量抖动；逐项记录位姿连续性、协方差、地图门控和安全停止行为。 |
| P2 | 接入真实履带/轮位移或其他纵向地标，并做打滑检测；`cmd_vel` 只作为命令记录，不作为里程真值。 | 补足长廊纵向观测。 | 地面量距/地标对照下的长廊往返误差；打滑与转弯工况下的鲁棒性。 |
| P3 | 若 P0–P2 仍不足，再评估二维激光几何残差＋IMU 预积分/ESKF 的专门前端，或更换有逐点时间的适配传感器；随后再调回环。 | 在已有可靠时空标定及独立纵向观测基础上提升动态性能。 | 与纯激光和松耦合 EKF 的同包、同路线对照；计算量、延迟与精度的收益。 |

门槛不应靠提高数字来“修好”。例如 1.5 m/s² 与现场分布显著冲突，既可能是阈值不合实际工况，也可能是安装、标定或数据损坏；只有取得实际运动参考并复核原始样本后，才能重新设定阈值和协方差。轮速也不是无条件真值：履带打滑时应降权或拒收。

## 八、建议用于会议的结论表述

> 这次集成的主要问题是系统架构与目标场景之间存在缺口：长廊最需要纵向位移观测，而现有惯导主要增加短时航向和不稳定的加速度预测，没有提供可靠的独立纵向距离。与此同时，传感器越限、时间不确定和保护状态切换让原本连续的纯激光链路出现多次暂停及建图输入中断。时间修复降低了 TF 丢扫描，但没有证明地图精度改善；回环是否造成漂移也尚无配对证据。下一阶段应先完成同包受控对照和数据时间标定，再引入可信位移约束，最后评估紧耦合与回环参数，而不是继续单独放宽保护阈值。
